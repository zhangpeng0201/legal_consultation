# 法询 · 法律法规智能问答

用日常语言描述问题，系统从 **309 部现行法律法规、22,260 条法条**中检索依据，大模型**只基于检索到的条文**作答，并标注法规全称与条号；依据不足以回答时明确拒答。

> 核心不变量：**答案里的每一条结论，都必须能落到一条具体法条上。**

---

## 效果

60 题评测集（条号直查 / 口语描述 / 应拒答 各 20 条），本地 CPU，2026-10。

### 检索层（离线，40 条正例）

| 指标 | 结果 |
|---|---|
| Hit@1 | 25/40 = 62.5% |
| Hit@3 | 31/40 = 77.5% |
| Hit@5 = Hit@10 | **33/40 = 82.5%** |
| MRR | **0.7029** |

按题型拆开，弱项无法被平均数掩盖：

| 题型 | Hit@5 | Hit@1 | MRR |
|---|---|---|---|
| 条号直查（「刑法第232条」） | **20/20 = 100%** | 20/20 | **1.0000** |
| 口语描述（「东西从楼上掉下来砸到人」） | 13/20 = 65% | 5/20 | 0.4058 |

### 端到端（判定 → 引用 → 生成，60 条，两遍复跑）

| 环节 | 分母是什么 | 第一遍 | 第二遍 |
|---|---|---|---|
| 负例正确拒答 | 20（全部负例） | **20/20 = 100%** | **20/20 = 100%** |
| 正例判为「可答」 | 40（全部正例） | 33/40 = 82.5% | 32/40 = 80% |
| judge 引用命中标注条文 | 40（全部正例） | 32/40 = 80% | 32/40 = 80% |
| 答案里带正确条号 | 已生成条数（判真后才生成） | 30/33 = 90.9% | 29/32 = 90.6% |
| **整体判定准确率** | **60（全部，无排除）** | **53/60 = 88.3%** | **52/60 = 86.7%** |

60 条一条不排除，三类严格 20/20/20，所以整体指标的分母就是 60。

两遍只差一条：`s09`（网上被骗钱，骗子判几年）第一遍检索没召回却被判成「可答」，第二遍判对——**这一条是反向风险**，判定层放过了没有依据的问题，靠引用层把它兜住了（evidence 里不含标注条文）。其余 59 条判定结论、失败名单完全一致。

把两环串起来看，**端到端一次通过（判真 + 条号正确）= 30/40 与 29/40（75% / 72.5%）**。

### 错误归因（比百分比更有用）

两遍合计 8 条误拒，拆开看：

```
7 条 = 检索层根本没召回（s03 / s04 / s08 / s09 / s14 / s19 / s20）
1 条 = judge 漏读 context 第一条（z14，隔离连跑 5 次 → 3 真 2 假，抖动 40%）
```

→ 结论：**判定层天花板 = 检索层 Hit@5 = 33/40**。第二遍 32/40 正好贴住这个天花板；第一遍的 33/40 里有一条是 `s09` 被误判成「可答」，属于虚高，不算数。judge 在那 7 条上并没有误判，它准确识别出了「召回到的条文离题」。要提分应该改检索，不是改 prompt。

### 延迟（单轮，本地 CPU）

| 阶段 | 耗时 |
|---|---|
| 检索（三路 + RRF） | 0.3 s |
| judge 判定 | 1.6 s |
| 生成 | 2.6 s |
| **预热后单轮合计** | **约 4.5 s** |
| 冷启动首轮（含模型 / 索引加载） | 约 9 s |

## 架构

```
用户提问
   │
   ├─（多轮）追问改写：把「那防卫过当呢」补全为独立问题
   ▼
┌──────────────────── 三路召回 ────────────────────┐
│  exact   法名 + 条号精确匹配      权重 3.0        │
│  bm25    jieba 分词 + 倒排索引    权重 1.0        │
│  embedding  bge-small-zh-v1.5     权重 1.0        │
└──────────────────────┬───────────────────────────┘
                       ▼
              RRF 融合（k=60）→ Top-5 条文
                       ▼
          judge：这 5 条能不能回答这个问题？
             ├─ 不能 → 据实拒答（不生成）
             └─ 能   → generate：结论 + 法律依据（原文）+ 分析
                       ▼
              SSE 流式返回 / JSON 返回
```

### 为什么用 RRF 而不是加权求和

三路分数量纲完全不同：exact 是 0/1，BM25 无上界，余弦相似度 0~1。加权前必须归一化，而归一化方式本身又要调参。RRF **只用排名不用分数**：

```
score(条文) = Σ  weight_c / (k + rank_c)        k = 60，rank 从 1 起
```

exact 给 3.0 的原因很直接：`3.0/61 ≈ 0.0492`，是 `1.0/61 ≈ 0.0164` 的 3 倍，所以只要条号查得到，它必然压过另外两路的头名——这正是「条号直查 20/20」的来源。

### 为什么判两层（judge + generate）

一步生成的问题是没有「拒答」这个动作。拆成两步后：judge 只输出结构化判定（`answerable / evidence / reason`），生成链只在判定为真时才启动。这带来两个好处：

1. 拒答是可解释的（reason 会说明缺什么）
2. 误拒能被归因到检索层还是判定层——这是上面那张归因表能存在的前提

判定标准写死在 prompt 里：条文须能**直接支撑**争议点；主题相关但不对应算 false；部分覆盖算 false；需要外部知识算 false；**拿不准一律 false**。

## 快速开始

### 1. 环境

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
pip install torch --index-url https://download.pytorch.org/whl/cpu    # CPU 版，别装默认版
```

Python 3.11（与 Dockerfile 一致）。

### 2. 准备模型

向量通道依赖本地模型，放到仓库根目录：

```
bge-small-zh-v1.5/      # 91.4 MB（BAAI/bge-small-zh-v1.5）
```

HuggingFace `BAAI/bge-small-zh-v1.5` 或 ModelScope `AI-ModelScope/bge-small-zh-v1.5` 均可下载。仓库不包含权重文件。

### 3. 构建索引

```bash
cd src

# BM25 倒排索引（11 MB）：首次检索时自动构建，也可手动预热
python -c "from bm25_search import load_or_build; load_or_build()"

# 向量索引（44 MB）：必须在 BM25 之后（复用其行号顺序）
python -c "from embedding_search import embed_documents, save_embeddings; save_embeddings(embed_documents())"
```

两者都落在 `output/`，已被 `.gitignore` 排除——换台机器按上面两条命令重建即可。

### 4. 配置密钥

在**仓库根目录**建 `.env`：

```env
DEEPSEEK_API_KEY=sk-xxxxxxxx
DEEPSEEK_URL=https://api.deepseek.com
DEEPSEEK_NAME=deepseek-chat
```

### 5. 启动

```bash
# 在仓库根目录执行
uvicorn service:app --app-dir src --host 127.0.0.1 --port 8000
```

打开 <http://127.0.0.1:8000/html/index.html>，或直接看 <http://127.0.0.1:8000/docs>。

## 评测

评测集在 `data/eval/golden_set.json`：**60 条，三类各 20 条**。

| 类型 | 数量 | 判什么 | 考察能力 |
|---|---|---|---|
| 条号直查 | 20 | 指定条号必须在返回结果里 | exact 通道 |
| 口语描述 | 20 | 标注条文须被召回 / 被引用 | 语义召回 |
| 应拒答 | 20 | 必须拒答 | 不臆造 |

三类必须等量，否则占比高的类型会拉高整体分数、掩盖弱项——实测口语描述的 Hit@1 只有 5/20，一旦权重变化，整体分数就会失真。

```bash
cd src

# 检索层：离线，约 5 秒
python eval_run.py                    # 可选 --topk 5（默认 10，召回深度固定 10）

# 端到端：调模型，约 3 分钟（正例 2 次调用 / 条，负例 1 次）
python eval_run_e2e.py                # 可选 --limit 10 / --ids z01,s11 / --no-answer
```

两份脚本都会把**配置指纹**写进结果文件：模型名、temperature、max_tokens、thinking 开关、top_k、语料 size+mtime、各源码文件 sha256 前 12 位。没有指纹的数字，过两个月就没人说得清是在什么状态下跑出来的。

两个刻意设计的口径：

- **证据比对用子集判定**（`set(must_hit) ⊆ set(evidence)`）。judge 多引一条相关条文不算错，用全等比较会把「答得更全」判成失败。
- **负例必须一刀切干净**：只收「语料里确实查不到依据」的问题。凡是「条文能部分支撑、但要靠解释才能推出结论」的，一律不留在负例里，换掉。这类题留在集合里只能靠打补丁式豁免维持指标——第一版就踩过：`n10`「劳动仲裁申请书怎么写」其实仲裁法 28 条明确列了应载明事项、`n09`「被骗的钱能追回吗」反电诈法 34 条讲追赃挽损、`n14`「网课能全额退款吗」消保法 25 条给了除外情形。**三条都被换掉，60 条硬指标全部计入，不设例外。**

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/ask` | 单轮问答，返回结构化结果（`answerable / evidence / reason / answer`） |
| POST | `/ask/stream` | 多轮流式问答，SSE 推送 |
| GET | `/html/index.html` | 前端页面 |
| GET | `/docs` | OpenAPI 文档 |

```json
{ "query": "高空抛物砸伤人谁负责", "session_id": null }
```

`session_id` 为 `null` 时新建会话，服务端通过首个 `session` 事件下发标识；事件类型为 `session` / `delta` / `done`，按 `\n\n` 分帧。

## 已知限制

- **语料范围**：309 部常用法律，地方性法规、司法解释、部门规章未收录；问地方政策会拒答。
- **口语题召回**：40 条正例中 7 条未召回，全部是「无术语的纯口语」（如「被骗了钱怎么追回来」），关键词与语义两路都没抓住。
- **条号直查偶发漏读**：`z14` 这类题，检索第 1 位就是正确条文，judge 仍可能漏读 context 首条，隔离复跑 5 次抖动率 40%。
- **判定层有反向风险**：检索没召回到正确条文时，judge 偶尔仍判「可答」（`s09` 两遍里出现 1 次），此时答案会建立在离题条文上。目前靠引用层发现，生产环境应把「evidence 不涉及争议点」也作为拒答条件。
- **会话不落库**：历史存在进程内存、单实例，重启即清空；多实例部署需换 Redis。
- **串行链路**：judge 与 generate 串行，单轮约 4.5 s，尚未做并行或缓存。
